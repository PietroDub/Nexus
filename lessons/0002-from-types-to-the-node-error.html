O que é um tipo, o que é um return, e por que o Node vermelhou

A lição 1 começou no meio. Esta começa no chão: valor, tipo, anotação, Promise — e só no fim o teu findAll.

  1. Há duas épocas no teu código. Quando escreves TypeScript, o compilador lê o ficheiro antes de a API correr. Quando a API já está no ar (npm run start:dev), o Node.js executa JavaScript. Tipos não existem nessa segunda época. Eles só guiam o compilador. Um erro vermelho no VS Code é da primeira época. O Postgres nem vê isso.
  2. Valor é o que existe de verdade. "Pietro" é um valor. 26 é um valor. O objeto que o Prisma monta na memória depois do SELECT é um valor. Podes imprimir um valor no console.
  3. Tipo é o conjunto de valores permitidos. O tipo string significa “qualquer texto”. O tipo number significa “qualquer número”. O tipo boolean é só true ou false.
    Handbook: primitives string, number, boolean. Everyday Types.
  4. Uma anotação é um contrato escrito à mão. 
    let nome: string = "Pietro";
    Os : string vêm depois do nome. Querem dizer: “deste sítio em diante, nome só pode receber texto.” Se escreveres nome = 26, o compilador recusa — não porque o JavaScript não consiga, mas porque tu prometeste string.
    “Type annotations will always go after the thing being typed.” Annotations on variables.
  5. Funções têm dois contratos: entrada e saída. 
    function idade(n: number): number {
  return n;
}
    n: number = o argumento tem de ser número. (): number = o que a função return tem de ser número. Se deres return "vinte", o compilador recusa.
    “Return type annotations appear after the parameter list.” Return type annotations.
  6. Node[] significa “lista de Node”. O [] aplica-se ao tipo à esquerda. string[] = lista de textos. Node[] = lista de coisas que cabem no tipo chamado Node. Ainda não dissemos o que Node é — só que o array inteiro tem de ser homogéneo.
  7. Promise<T> significa “ainda não tenho T; vou ter T daqui a pouco”. findMany fala com o Postgres. Isso demora. Por isso não devolve o array imediatamente: devolve uma Promise. A anotação oficial para isso é Promise<T>, onde T é o que aparece quando a Promise resolve.
    “If you want to annotate the return type of a function which returns a promise, you should use the Promise type.” Functions which return Promises.
    Então Promise<Node[]> lê-se, em voz alta: “prometo, no futuro, uma lista de Node.”
  8. O teu método, traduzido para português. 
    findAll(): Promise<Node[]> {
  return this.prisma.node.findMany();
}
    “Esta função, no futuro, entrega uma lista da minha classe Node. O valor que estou a devolver é o que o Prisma.findMany produzir.” O compilador compara as duas pontas desta frase.
  9. De onde vem o tipo da tua classe Node. O import: 
    import { Node } from "../models/node.model.js";
    aponta para o ficheiro que tu escreveste. Lá existia (antes da correção): 
    export class Node {
  id: string;
  title: string;
  attributes: Record<string, unknown>;
  // ...outros campos
}
    Isto é um tipo objeto: uma lista de propriedades e os tipos de cada uma. Object Types.
  10. De onde vem o tipo que o Prisma devolve. npx prisma generate lê o schema.prisma e gera ficheiros em src/generated/prisma. O campo attributes Json vira, no cliente, o tipo JsonValue. Não é a tua classe. É outro mapa de propriedades, gerado automaticamente. Os dois se chamam “Node” na conversa. No compilador, são dois mapas.
  11. TypeScript não casa tipos pelo nome. Casa pela forma. Se o alvo pede { nome: string }, qualquer valor com um nome: string serve — mesmo que a classe se chame Dog. Se falta um membro, ou um membro tem tipo mais largo do que o alvo aceita, recusa.
    “x is compatible with y if y has at least the same members as x.” Type Compatibility.
  12. Comparação membro a membro — User primeiro, porque funciona. Alvo = tua classe User. Fonte = linha Prisma de users. id string/string, email string/string, displayName string/string, datas Date/Date. Todos os membros do alvo existem na fonte com o mesmo tipo. O contrato fecha. Por isso Promise<User[]> aceita findMany.
  13. A mesma comparação no Node — pára em attributes. id, title, content: iguais. Depois:
    Alvo (tua classe, antes)Fonte (Prisma)
    attributesRecord<string, unknown>JsonValue
  14. União: “isto ou aquilo”. string | number aceita texto ou número. Union Types. O Prisma declara: 
    JsonValue = string | number | boolean | null | JsonObject | JsonArray
    Ou seja: attributes pode ser null, ou um array, ou um número. Isto espelha o que JSON.parse aceita. Prisma Json.
  15. Record<string, unknown> é só objeto. Significa: “um objeto cujas chaves são string e cujos valores são unknown.” Record. { "level": 1 } cabe. null não cabe. [1, 2] não cabe. A fonte (JsonValue) permite null. O alvo (Record) proíbe null. A fonte é mais larga que o alvo. Atribuição ilegal.
  16. Uma analogia física. O alvo é a boca de um funil: só passa objeto. A fonte é um balde onde também pode vir líquido (null) ou uma lista. O compilador recusa despejar o balde no funil — mesmo que tu, na prática, só coloques objetos no balde. Ele olha para o tipo do balde, não para o que tu costumas pôr lá.
  17. Por que o erro menciona then. Promise<A[]> só é atribuível a Promise<B[]> se A[] for atribuível a B[]. O compilador entra no Promise, encontra o método then, e compara o value do callback. Lá está o array. Lá o passo 15 falha. A mensagem enorme é o envelope (Promise) a mostrar o conteúdo (attributes).
  18. O que a correção fez — e o que não fez. Mudámos o alvo: 
    attributes: Prisma.JsonValue;
    O funil passou a ter a mesma boca do balde. Campo a campo, a comparação fecha. findMany não mudou. O Postgres não mudou. Só o contrato da tua classe. Não usámos as Node[]: isso seria rasgar o contrato em vez de o alinhar.
