Por que o return não type-checkava — passo a passo

Já localizaste o sítio: a anotação Promise<Node[]>. Esta lição não salta daí para “é o JSON”. Cada passo é o que o compilador faz a seguir.

  1. O método faz uma query. 
    findAll(): Promise<Node[]> {
  return this.prisma.node.findMany();
}
    Em runtime isto funciona: o Prisma vai ao Postgres e devolve linhas. O erro é só de tipos, em tempo de compilação.
  2. A anotação é um contrato, não um rótulo. Escrever : Promise<Node[]> significa: “o que esta função devolve tem de ser atribuível a um array da minha classe Node.” O TypeScript vai verificar isso. Não traduz o nome Node para “o modelo Prisma Node”.
  3. Existem dois tipos diferentes que tu chamaste Node. Um é api/nexus-api/src/models/node.model.ts — a classe que importaste. O outro é o tipo gerado em src/generated/prisma, que descreve a linha da tabela nodes. Partilham o nome na tua cabeça. No compilador são dois contratos separados.
  4. TypeScript é estrutural: ignora o nome, lê os membros. A regra oficial: um valor é compatível com um tipo se tiver pelo menos os mesmos membros, cada um compatível.
    Handbook: “x is compatible with y if y has at least the same members as x.” Type Compatibility.
  5. Ele compara campo a campo com a tua classe como alvo. Alvo = o que prometeste (Node da model). Fonte = o que o Prisma devolve. Para cada propriedade do alvo, tem de haver uma propriedade compatível na fonte.
  6. User passa neste teste. Por isso o UserService não vermelhou.
    CampoTua classe UserPrisma User
    idstringstringok
    emailstringstringok
    displayNamestringstringok
    createdAtDateDateok
    Todos os membros do alvo existem na fonte com o mesmo tipo. Atribuição permitida. findMany de User encaixa em Promise<User[]>.
  7. Node começa igual — até attributes.
    CampoTua classe (antes)Prisma Node
    idstringstringok
    titlestringstringok
    contentstringstringok
    attributesRecord<string, unknown>JsonValuefalha
    Um membro incompatível anula o objeto inteiro. Não há “quase Node”.
  8. O que cada tipo de attributes aceita. Record<string, unknown> é um objeto cujas chaves são string. Oficialmente: “object type whose property keys are Keys and whose property values are Type.” Record. Valores legais: { "level": 1 }. Ilegais: null, [1,2], "texto", true.
  9. O Prisma modela JSON de verdade. Campo Json no schema vira JsonValue: 
    string | number | boolean | null | JsonObject | JsonArray
    Isto existe para coincidir com o que JSON.parse pode devolver. Prisma Json fields. null é um JsonValue. null não é um Record. Portanto JsonValue não é atribuível a Record<string, unknown> — mesmo que tu só graves objetos.
  10. Por que o erro fala de then e onfulfilled. findMany devolve PrismaPromise<Linha[]>, que é um Promise. Para um Promise ser atribuível a outro, o valor resolvido tem de ser atribuível. O compilador desce a then, depois ao callback, depois a value. Lá, Linha[] vs Node[] falha no passo 7. A pilha enorme é só o Promise a empacotar o mesmo problema de attributes.
  11. A correção do tipo: o alvo passou a falar a língua da fonte. Na model: 
    attributes: Prisma.JsonValue;
    Agora o alvo aceita o mesmo conjunto que o Prisma devolve. Campo a campo, a comparação fecha. return this.prisma.node.findMany() passa a ser atribuível a Promise<Node[]>. Não usámos as Node[]: isso calava o erro mentindo. Alinhámos o contrato.
  12. Duas correções vizinhas — não são o erro do return, mas estavam no mesmo ficheiro. O schema não tem description; o campo é content. E JSON.stringify(dto.attributes) transformava o objeto numa string; o Prisma já serializa objetos para Json. Writing to a Json field. Isso quebraria o create, não o tipo do findAll.
