Três tabelas, uma cadeia — não três Users

As lições 1–2 eram sobre tipos. Esta é sobre quem é pai de quem no Nexus, para implementares View sem inventar um POST /graphs.

  1. Três trabalhos, três nomes. No GLOSSARY:
    • Graph — o conjunto de nodes e relations. É o conhecimento. Não é o desenho.
    • View — recorte visual: nome, viewport, filtros, “esta é a default?”. Não muda o significado dos nodes.
    • Layout — um par (x, y) de um node numa view. A palavra “layout” no glossário é mesmo a geometria, não a View.
    Se metesses x,y no Node, arrastar o canvas versionaria o conhecimento. O ADR 0001 recusa isso.
  2. Relação no banco = chave estrangeira, não “três CRUDs iguais”. Uma linha filha guarda o id do pai. Muitas filhas podem apontar para o mesmo pai. Isso chama-se um-para-muitos.
    Prisma: o filho guarda o id do pai; o pai declara uma lista. Relation queries (v6, API do teu Prisma 7).
    No teu schema: 
    graphs.workspace_id     → workspaces.id
graph_views.graph_id    → graphs.id
graph_view_layouts.view_id → graph_views.id
graph_view_layouts.node_id → nodes.id
    Layout tem dois pais: a view (onde está desenhado) e o node (o que está desenhado).
  3. A árvore, desenhada. 
    Workspace
  └── Graph              ← conhecimento vive aqui
        ├── Node[]
        ├── Relation[]
        └── GraphView[]  ← apresentação
              └── GraphViewLayout[]   (viewId + nodeId + x + y)
    User é uma linha solta. Graph não. Graph pertence a um workspace. View pertence a um graph. Layout pertence a uma view e a um node.
  4. Nested write: o pai cria o filho no mesmo INSERT. Prisma deixa-te, num único create, escrever o pai e os filhos. Se qualquer parte falhar, nada fica gravado (transação).
    “A nested write allows you to write relational data to your database in a single transaction.” Nested writes.
    É exatamente o que o WorkspaceService.create já faz: 
    workspaces.create({
  graphs: {
    create: {
      name: dto.name,
      views: {
        create: {
          name: "Default",
          isDefault: true,
          createdBy: dto.ownerId,
        },
      },
    },
  },
})
    Um POST /workspaces já abre: 1 workspace, 1 graph, 1 view Default. Zero layouts. Layouts precisam de um node, e ainda não há nodes.
  5. O que existe no banco depois desse POST.
    TabelaLinhas
    workspaces1
    graphs1 (nome = nome do workspace)
    graph_views1 (Default, isDefault: true, viewport {x:0,y:0,zoom:1})
    graph_view_layouts0
    nodes / relations0 (vocabulário de tipos já está copiado)
    Por isso não há POST /graphs: a linha já nasceu. Implementámos só leitura e rename.
  6. Contrato HTTP do Graph — já feito. Nest agrupa rotas com um prefixo no @Controller. @Get(':id') captura o id do URL. @Query lê a query string. @Patch é atualização parcial.
    Nest controllers: prefixo, @Get(':id'), @Query, @Patch.
    RotaFaz
    GET /graphs?workspaceId=Lista (MVP: 0 ou 1). Ignora workspace arquivado.
    GET /graphs/:idA linha do graph. Sem nodes, sem x,y.
    PATCH /graphs/:id{ name? }. Não mexe em schemaVersion.
    GET /workspaces/:id já traz graphs[].views no detalhe — é o include aninhado, não um segundo create.
  7. View — a primeira linha já existe; o CRUD ainda não. Depois do workspace, podes abrir a Default (se souberes o id pelo detalhe do workspace). Não podes ainda:
    • listar views por graphId
    • criar uma segunda view
    • mudar viewport / filters / nome / default
    • apagar uma view extra
    Contratos a implementar, no mesmo estilo do Graph (recurso plano /views): 
    GET    /views?graphId=
GET    /views/:id
POST   /views          { graphId, name, createdBy }
PATCH  /views/:id      { name?, viewport?, filters?, isDefault? }
DELETE /views/:id
    Regras que o User não tem:
    • Um default por graph. Promover uma view, na mesma transação, desmarca as outras.
    • Não apagar a última view. Não ficar sem default.
    • View não tem archivedAt: DELETE é hard delete; layouts caem por CASCADE. Nodes ficam.
    • version da view sobe no PATCH de metadados. Audit ViewUpdated aqui — não no drag.
    O assert da View é só “este graphId existe e o workspace não está arquivado”. Não copies o assertPlacement da Relation.
  8. Layout — não é um recurso REST com id. A identidade é a PK composta (viewId, nodeId). Um node na view A tem um (x,y); na view B pode ter outro; ou nenhum (ainda não abriste essa view).

    O canvas não faz POST + PATCH linha a linha. Faz upsert: “se esta chave existe, atualiza x,y; senão, cria.”

    Prisma upsert: where (único), update, create. Update or create records.
    Contrato único: 
    PUT /views/:viewId/layouts
[{ "nodeId": "...", "x": 12.5, "y": 40 }]
    Vive no mesmo GraphViewService, não num GraphViewLayoutService tipo User. O assert: cada node existe, não está arquivado, e node.graphId === view.graphId. A FK sozinha não garante o mesmo graph.
  9. Fluxo humano, passo a passo, com o que já corre.
    1. POST /workspaces → nasceram graph + view Default. Layouts = 0.
    2. GET /graphs?workspaceId= ou o detalhe do workspace → pegas o graphId.
    3. POST /nodes com esse graphId → conhecimento. Ainda zero layouts. O NodeService.create não escreve graph_view_layouts.
    4. Front abre o canvas da Default. GET /views/:id (quando existir) devolve viewport + lista de layouts (vazia). Junta com GET /nodes. Nodes sem layout aparecem num sítio provisório (centro do viewport).
    5. Arrastas → PUT /views/:id/layouts. Aí nasce a primeira linha de layout. Só nesta view.
    6. Segunda view (quando o POST existir) começa sem layouts. O mesmo node, outra geometria.
  10. O que já vem “de graça” vs o que falta destes dois.
    PeçaJá tensFalta
    Graph Linha (workspace). GET/PATCH. Model. Nada neste fluxo.
    GraphView Linha Default (workspace). Model. Prisma. Service, DTOs, controller, regra do default, DELETE seguro.
    Layout Tabela, model, PK composta, CASCADE. Método upsertLayouts + rota PUT. Zero linhas até o canvas escrever.
    Ordem: View CRUD primeiro (senão o PUT não tem pai). Layout a seguir, no mesmo service. Não implementes os dois em paralelo como se fossem User e Node.
  11. Armadilha de tipos que já viste. O model GraphView tem viewport: Viewport e filters: Record<string, unknown>. O Prisma devolve JsonValue nos dois. É o mesmo fosso do attributes na lição 2. Quando fores escrever o service, alinha o model a Prisma.JsonValue ou valida e estreita na borda — não copies Record outra vez.

Pratica

Fonte primária de domínio: Modelo de dados (§ graphs, graph_views, graph_view_layouts). Nested write: Prisma nested writes. Rotas: Nest controllers.

Folha: contratos Graph / View / Layout.
